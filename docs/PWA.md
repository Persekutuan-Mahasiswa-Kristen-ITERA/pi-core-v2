# PI-CORE v2 — PWA notes

PI-CORE is installed from the browser: **Safari → Share → Add to Home Screen** on iOS, the install prompt or
**⋮ → Install app** in Chrome on Android. No App Store, no Apple Developer account.

## What makes it installable

| Item           | Where                                                                   | Value                                                                                                 |
| -------------- | ----------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| Manifest       | `src/app/manifest.ts` → `/manifest.webmanifest`                         | `display: standalone`, `start_url` and `scope` `/`, portrait, theme/background `#f8f7f6`              |
| Icons          | `public/icons/`                                                         | 192 + 512 (`any`), 192 + 512 (`maskable`, seal inside the safe zone), 180 `apple-touch-icon` (opaque) |
| Service worker | `public/sw.js`, registered in production by `ServiceWorkerRegistration` | see below                                                                                             |
| iOS meta       | `src/app/layout.tsx` metadata/viewport                                  | `viewport-fit=cover`, `apple-mobile-web-app-capable`, title, status bar `default`                     |
| Safe areas     | `--safe-*` CSS variables                                                | top bar, bottom nav, drawer, login header and offline page pad with `env(safe-area-inset-*)`          |
| No 100vh bugs  | `min-h-dvh` everywhere                                                  | dynamic viewport units                                                                                |

Icons are generated by `scripts/generate-icons.py` from the 500×500 PMK logo (every output is a downscale). A
vector or ≥1024px logo would give sharper large icons; replace the source and re-run the script.

## Service worker caching strategy

| Request                                                     | Strategy                                | Why                                               |
| ----------------------------------------------------------- | --------------------------------------- | ------------------------------------------------- |
| Page navigations (HTML)                                     | **Network only**, `/offline` on failure | HTML is per user and per permission; never stored |
| `/_next/static/*`                                           | Cache first                             | Content-hashed, no user data                      |
| `/icons/*`, `/brand/*`                                      | Cache first                             | Public images                                     |
| RSC payloads, Server Actions, Supabase API, everything else | Not intercepted                         | Data and authorization must always be fresh       |

Precache: `/offline`, logo, one icon. Old caches are deleted on activation (bump `VERSION` in `sw.js` when its logic
changes). `sw.js` is served with `Cache-Control: no-cache` so updates are picked up. Because nothing user-specific
is ever in Cache Storage, logout or switching accounts cannot show another person's data, and a revoked admin never
sees a cached admin page.

## Session persistence in standalone mode (iOS)

- Supabase SSR sessions live in cookies (`sb-<ref>-auth-token*`, 400-day max-age, `SameSite=Lax`).
- Safari ITP caps cookies written by JavaScript at 7 days. Login runs in the browser, so right after sign-in a Server
  Action re-sets the same cookies through `Set-Cookie` (`src/app/login/actions.ts`). `proxy.ts` also re-sets them on
  every token refresh. Expected result: members stay logged in across launches until they log out.
- Home-screen apps on iOS have their own cookie jar, separate from Safari: logging in in Safari does not log in the
  installed app, and the other way round. Members log in once inside the installed app.
